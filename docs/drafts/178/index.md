# フィーチャーフラグ — コードを出すことと機能を見せることを分ける

## 今日のゴール

- コードを本番に出すことと、機能を利用者に見せることは分けられると知る
- フラグは `if` 文だが、値がコードの外にあるので人を選んで切り替えられると分かる
- 消す条件を決めずに足すと、フラグが溜まって手に負えなくなると知る

## 新機能が人によって出たり出なかったりする

いつも使っているアプリの新機能が、隣の人の画面にはもう出ているのに、自分の画面にはまだ出ていないことがあります。アプリを更新した覚えがないのに、ある日突然画面が新しくなっていることもあります。お知らせを見ると「順次提供します」と書いてあったりします。

こちらは何もしていないのに機能が現れるのだから、出すか出さないかはサービス側が切り替えています。それも、全員一斉ではなく人を選んで切り替えています。

## 見せるかどうかをコードが握っている

ふつうに作ると、機能を見せるかどうかを決めているのはコードそのものです。そのコードが本番に入っていれば見えるし、入っていなければ見えません。

この状態だと、見せるかどうかを変えるたびにコードを触ることになります。まだ見せたくないものは本番に入れられません。いったん出したものを引っ込めるなら、コードを直して、ビルドして、本番に配り直すしかありません。それが終わるまで、見せたくない画面は見え続けます。

だから、**コードを本番に出すことと、機能を利用者に見せることを、別々に操作したい**わけです。これをできるようにするのが**フィーチャーフラグ**です。フィーチャートグルとも呼ばれます。

## 分岐にひとつ挟むだけ

やることは、機能をひとつの分岐で包むことです。

```jsx
import { isEnabled } from "./flags";

export default function OrderPage() {
  return (
    <div>
      <OrderSummary />
      {isEnabled("new-payment-flow") && <NewPaymentFlow />}
    </div>
  );
}
```

これで新しい決済フローのコードは本番に入っていますが、`isEnabled` が false を返すあいだ画面には出てきません。オンにするとき、コードは触りません。

## 値がコードの外から来る

書き方としては `if` 文です。違うのは、**その値がコードの中に書かれていない**ことです。値の置き場所は環境変数だったり、データベースや専用のサービスだったりしますが、どれにしてもコードの外にあります。

値をコードに書いてしまうと（`const ENABLED = false` のように）、それはフラグではなく普通の分岐です。切り替えるたびにコードの変更が必要になります。

値が外にあるから、コードを変えずにオンとオフを行き来できます。さらに置き場所によっては、**人によって違う値を返せます**。社内の人だけオン、10%の利用者だけオン、という出し分けです。「隣の人には出ているのに自分には出ていない」は、これが起きている状態です。

- **環境変数**: いちばん手軽。ただし値を変えるには再起動が要り、全員が同じ値になる
- **データベースや専用のサービス**: 値を変えるとすぐ反映され、利用者ごとに変えられる

この出し分けができると、いきなり全員に出さずに済みます。まず社内の人だけ、次に1%、10%と様子を見ながら広げれば、問題があったときに踏む人を減らせます。そして問題が出たときは、値をオフに戻すだけです。ビルドや配り直しを待たずに、壊れた画面を引っ込められます。

似た話で**カナリアリリース**という言葉も出てきますが、あちらは新しいバージョンを一部のサーバーにだけ配って、アクセスの一部をそちらに流す方法です。バージョンまるごとが単位で、切り替えるのはインフラ側になります。フラグは機能ひとつが単位でコードの中で切り替えるので、機能ごとに別々に止められます。

## 未完成のコードも本番に置ける

見せるかどうかを分岐が握っているなら、まだ完成していない機能も同じやり方で隠せます。作りかけのコードを、オフのまま統合先（チーム全員の変更が集まるブランチ）に入れておけるということです。

これができないと、完成まで自分のブランチ（本番のコードから分けた、自分用の作業コピー）で抱えることになります。抱えているあいだも他の人は統合先を変え続けるので、ブランチは日が経つほど周りから離れます。離れたぶんのズレは最後のマージでまとめて解消することになり、3日分と3か月分では衝突の数も1件ごとの難しさも変わります。

未完成をフラグで隠しながら、小さくこまめに統合先へ入れ続ける進め方を**トランクベース開発**と呼びます。長生きするブランチを作らないための進め方です。

コードが入った状態で待てるので、公開の日も選べるようになります。出す準備と出す判断を、別々に進められます。

## 4つの使い道

ここまでは新機能を出す話でしたが、同じ仕掛けは別の目的にも使われます。よく使われる整理では4つに分かれます。

| 種類 | 何のために | 寿命 |
|---|---|---|
| リリース | 未完成のコードを本番に置いておく | 短い。出したら消す |
| 実験 | A/B テストのように、利用者を分けて比べる | 一時的。決まったら消す |
| 運用 | 負荷が高いときに重い機能を止めるなど | 長い |
| 権限 | 契約プランや役割によって出し分ける | ずっと残る |

同じ `if (flag)` でも、寿命と切り替えの頻度が違います。数日で消すつもりのものと、ずっと残るものを同じ扱いにすると、あとで区別がつかなくなります。

A/B テストも、この表のとおりフラグの一種として実装されます。仕組みは同じ `if` 文で、どちらを見せるかを乱数で振り分けて、あとで結果の数字を比べます。

## 足すのは簡単で消すのは難しい

フラグを足すのは簡単です。分岐をひとつ書くだけです。難しいのは消すほうで、オンにして問題が出なければそのまま動いてしまうので、わざわざ触る理由がなく、放っておくと誰も消しません。

そして数が増えると、分岐は掛け算で増えます。

| フラグの数 | 組み合わせ |
|---|---|
| 1 | 2 通り |
| 3 | 8 通り |
| 10 | 1024 通り |

全部を試すことはできません。実際に確かめられるのは、そのうちのごく一部です。残りの組み合わせは、動くかどうか誰も確かめないまま本番に置かれています。

役目を終えたフラグも、放っておいても消えるわけではありません。オフのまま残った古い分岐は、値がひとつ変われば動き出せる状態で居座り続けます。コードを読む人にも、生きている分岐と終わった分岐の区別がつきません。

## 足す時点で消す条件を決める

だから、足す時点で決めておきます。何が起きたらこのフラグは要らなくなるのか、誰が消すのか、オンにしたあといつまで分岐を残すのか。

上の表の「寿命」の列が効くのはここです。ずっと残る権限のフラグと、出したら消すリリースのフラグを、同じ名前の付け方や同じ置き場所で管理すると、どれが消せるのか分からなくなります。

## まとめ

- フラグを挟むと、コードを出すことと機能を見せることが別々になる
- 値がコードの外にあるので、人を選んで出せて、その場で引っ込められる
- 足すのは簡単で消すのは難しいので、入れる時点で消す条件を決める
