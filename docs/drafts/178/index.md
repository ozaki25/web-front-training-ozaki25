# フィーチャーフラグ — コードを出すことと機能を見せることを分ける

## 今日のゴール

- コードを本番に出すことと、機能を利用者に見せることは分けられると知る
- フラグは `if` 文だが、値がコードの外から来る点が違うと分かる
- 消す条件を決めないと、残ったフラグが事故になると知る

## 出したものはそのまま見えてしまう

本番に出したものは、そのまま利用者に見えます。だから「まだ見せられない機能」は本番に入れられません。作りかけのものは自分のブランチで持っておいて、完成してから出す。ふつうはそう考えます。

同じ理由で、機能をオフにしたいときもコードを直すことになります。挙動をひとつ変えるために、ビルドし直して、確認して、また本番に出す。

**この2つを分けられるようにする**のがフィーチャーフラグです。コードは本番に置くが、機能は見せない。オンとオフの切り替えに、コードの変更もビルドも要らない。

## 分岐にひとつ挟むだけ

やることは、機能をひとつの分岐で包むことです。

```jsx
export default function OrderPage() {
  return (
    <div>
      <OrderSummary />
      {isEnabled("new-payment-flow") && <NewPaymentFlow />}
    </div>
  );
}
```

これで新しい決済フローのコードは本番に入っていますが、`isEnabled` が false を返すあいだ画面には出てきません。完成したらオンにするだけで、コードは触りません。

## 値がコードの外から来る

書き方としては `if` 文です。違うのは、**その値がコードの中に書かれていない**ことです。環境変数から読む、データベースから引く、専用のサービスに問い合わせる。どれにしても、値はコードの外にあります。

値をコードに書いてしまうと（`const ENABLED = false` のように）、それはフラグではなく普通の分岐です。切り替えるたびにコードの変更が必要になります。

外にあることで、2つのことができます。

- **コードを変えずに切り替えられる**。ビルドし直さずにオンとオフを行き来できる
- **人によって違う値を返せる**。社内の人だけオン、10%の利用者だけオン、といった出し分けができる

## 分けられると何ができるか

この2つが揃うと、いくつかのことが同時に手に入ります。

**未完成を本番に置ける。** 作りかけのコードを、オフのまま統合先に入れておけます。これができないと、完成までブランチで抱えることになります。抱えているあいだも他の人は統合先を変え続けるので、ブランチは日が経つほど周りから離れます。離れたぶんは最後にまとめて払うことになり、3日分と3か月分では衝突の数も1件ごとの難しさも変わります。

**出す日を選べる。** コードが入っている状態で待てるので、公開のタイミングを開発の進み方から切り離せます。

**少しずつ出せる。** 全員に一度で出すと、問題があったとき全員が踏みます。1%、10%と広げていけば、踏む人を抑えられます。

**すぐ止められる。** 問題が出たとき、切り戻しの手順を通さずにオフにできます。直して出し直すまでのあいだ、壊れた画面を見せ続けずに済みます。

## 4つの使い道

同じ仕掛けが、目的によって別の顔をします。よく使われる整理では4つに分かれます。

| 種類 | 何のために | 寿命 |
|---|---|---|
| リリース | 未完成のコードを本番に置いておく | 短い。出したら消す |
| 実験 | A/B テストのように、利用者を分けて比べる | 一時的。決まったら消す |
| 運用 | 負荷が高いときに重い機能を止めるなど | 長い |
| 権限 | 契約プランや役割によって出し分ける | ずっと残る |

同じ `if (flag)` でも、寿命と切り替えの頻度が違います。数日で消すつもりのものと、ずっと残るものを同じ扱いにすると、あとで区別がつかなくなります。

A/B テストも、この表のとおりフラグの一種として実装されます。裏側は `if` 文で、振り分けを乱数でやり、あとで数字を見る。それだけの違いです。

## 足すのは簡単で消すのは難しい

フラグを足すのは簡単です。分岐をひとつ書くだけです。難しいのは消すほうで、放っておくと誰も消しません。

そして数が増えると、分岐は掛け算で増えます。

| フラグの数 | 組み合わせ |
|---|---|
| 1 | 2 通り |
| 3 | 8 通り |
| 10 | 1024 通り |

全部を試すことはできません。実際に確かめられるのは、そのうちのごく一部です。

## 2012年の証券会社

9年間使われていなかった古い機能が、フラグと一緒にコードに残っていました。新しい機能を入れるとき、そのフラグの名前を**使い回した**のです。

配信作業で8台のうち1台に新しいコードが届かず、その1台では同じフラグが古い機能を起動しました。45分で約4.4億ドルの損失。監督官庁の処分では、使われなくなったコードの起動を防ぐ仕組みがなかったことが指摘されています。

配信の漏れとフラグの使い回しが重なった事故で、フラグだけが原因ではありません。ただ、9年放置されたフラグが残っていなければ、この形にはなりませんでした。

## 足す時点で消す条件を決める

だから、足す時点で決めておきます。何が起きたらこのフラグは要らなくなるのか。誰が消すのか。オンにしたあと、いつまで分岐を残すのか。

上の表の「寿命」の列が効くのはここです。ずっと残る権限のフラグと、出したら消すリリースのフラグを、同じ名前の付け方や同じ置き場所で管理すると、どれが消せるのか分からなくなります。

## まとめ

- フラグを挟むと、コードを出すことと機能を見せることが別々になる
- `if` 文だが値がコードの外にあるので、コードを変えずに、人によって切り替えられる
- 足すのは簡単で消すのは難しいので、入れる時点で消す条件を決める
