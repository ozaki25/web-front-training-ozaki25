# フィーチャーフラグ — コードを出すことと機能を見せることを分ける

## 今日のゴール

- 作りかけをブランチに抱え続けると、マージがどんどん重くなると知る
- コードを本番に出すことと機能を見せることは、フラグで分けられると知る
- 消す条件を決めずに足すと、フラグが溜まって消えなくなると知る

## 作りかけの機能は人に見せられない

新しい機能を作っている途中、画面は中途半端な状態になります。ボタンはあるのに押しても何も起きなかったり、フォームが最後まで作れていなかったりする、あの状態です。人に見せるのは、ひととおり動くようになってからにしたいところです。

チームで開発すると、これは好みの問題ではなくなります。統合先（チーム全員の変更が集まるブランチ。`main` や、トランクとも呼ばれます）に入ったコードは、いずれそのまま本番に出ていって利用者に見えます。

だから作りかけの機能は統合先に入れられません。完成するまで自分のブランチに置いておく。ふつうはそう進めます。

## 抱えたブランチは統合先から離れていく

ところが、抱えているあいだも他の人は統合先を変え続けます。自分のブランチは日が経つほど周りから離れていきます。そのズレは、マージのときにまとめて解消することになります。3日分と3か月分では、衝突の数も1件ずつ解く難しさも変わります。

毎日こまめに統合先へ入れれば、ズレは小さいうちに解消できます。でも今度は、作りかけの機能が本番に出てしまいます。

- **完成まで抱える**: 見せずに済むが、マージがどんどん重くなる
- **毎日入れる**: マージは軽いが、作りかけが利用者に見えてしまう

どちらを選んでも困ります。この板挟みの原因は、**本番にコードがあることと、機能が利用者に見えることが、くっついている**ことです。ここを切り離せれば、毎日入れながら見せずに済みます。

## コードは入っているが画面には出てこない

これを切り離すのが**フィーチャーフラグ**です。フィーチャートグルとも呼ばれます。機能をひとつの分岐で包みます。

```jsx
import { isEnabled } from "./flags";
import OrderSummary from "./OrderSummary";
import NewPaymentFlow from "./NewPaymentFlow";

export default async function OrderPage() {
  const showNewFlow = await isEnabled("new-payment-flow");

  return (
    <main>
      <OrderSummary />
      {showNewFlow && <NewPaymentFlow />}
    </main>
  );
}
```

新しい決済フローのコードは本番に入っていますが、`isEnabled` が false を返すあいだ画面には出てきません。作りかけでも、オフのままなら毎日統合先に入れられます。マージを小さく保ちながら、機能は隠しておけます。

長生きするブランチを作らず、小さくこまめに統合先へ入れ続ける進め方を**トランクベース開発**と呼びます。フラグは、それを成り立たせるための道具です。

完成したらオンにします。コードはすでに本番に入っているので、公開の日は開発の都合と切り離して選べます。

## 値がコードの外から来る

`isEnabled` が返す値は、コードの中に書いてありません。環境変数だったり、データベースや専用のサービスだったりしますが、どれにしてもコードの外にあります。だからオンにするとき、コードもビルドも触らずに済みます。

値をコードに書いてしまうと（`const ENABLED = false` のように）、それはフラグではなく普通の分岐です。切り替えるたびにコードの変更とビルドが必要になり、「毎日入れて、見せずに待つ」が成り立ちません。

置き場所によって、できることが変わります。

- **環境変数**: いちばん手軽。ただし全員が同じ値になり、変えるにはサーバーの再起動が要る
- **データベースや専用のサービス**: 値を変えるとすぐ反映され、**人によって違う値を返せる**

Next.js で気をつけるのは、ブラウザ側で読む `NEXT_PUBLIC_` の環境変数です。この値はビルドのときにコードへ焼き込まれるので、あとから環境変数を変えてもアプリは反応しません。切り替えるには作り直しが要ります。

人によって値を変えられると、公開を少しずつ広げられます。まず社内の人だけオン、次に利用者の1%、10%と様子を見ながら広げ、問題が出たら値をオフに戻す。ビルドも配り直しも待たずに、壊れた画面を引っ込められます。

使っているアプリで、隣の人にはもう出ている新機能が自分にはまだ出ていない、ということがあります。あれはこの出し分けの途中です。コードはすでに全員に届いていて、見せる相手だけを少しずつ広げています。

似た言葉に**カナリアリリース**があります。あちらは新しいバージョンを先に一部にだけ当てて様子を見る方法で、サーバーを分けてアクセスの一部をそちらへ流す形が代表的です。バージョンまるごとが単位で、切り替えるのはインフラ側です。フラグは機能ひとつが単位で、コードの中で切り替えます。

## フラグには消すものと残るものがある

ここまでは新機能を出すためのフラグでしたが、同じ仕掛けは別の目的にも使われます。

| 種類 | 何のために | 寿命 |
|---|---|---|
| リリース | 未完成のコードを本番に置いておく | 短い。出したら消す |
| 実験 | A/B テストのように、利用者を分けて比べる | 一時的。決まったら消す |
| 運用 | 負荷が高いときに重い機能を止める | 多くは短い。備えとして残すものは長い |
| 権限 | 契約プランや役割によって出し分ける | ずっと残る |

運用のフラグは、アクセスが集中したときに重い機能だけ止めて、サービス全体が落ちるのを防ぐために使います。落ち着いたら消すものが多いですが、いつでも止められる備えとして残すこともあります。権限のフラグは、有料プランの人にだけ機能を出すような出し分けで、その機能がある限り消えません。

A/B テストも、多くの場合この実験用のフラグとして実装されます。仕組みは同じ `if` 文で、どちらを見せるかは利用者の ID から計算します。同じ人が毎回同じほうを見るようにしないと、結果を比べられません。

## 足すのは簡単で消すのは難しい

フラグを足すのは簡単です。分岐をひとつ書くだけです。難しいのは消すほうです。オンにして問題が出なければそのまま動いてしまうので、わざわざ触る理由がありません。放っておくと誰も消しません。

そして数が増えると、分岐は掛け算で増えます。

| フラグの数 | 組み合わせ |
|---|---|
| 1 | 2 通り |
| 3 | 8 通り |
| 10 | 1024 通り |

全部を試すことはできません。手が回るのはごく一部で、残りの組み合わせは、動くかどうか誰も確かめないまま本番に置かれています。

役目を終えたフラグも、そのままでは消えません。オフのまま残った古い分岐は、値をひとつ変えれば動き出してしまいます。コードを読む人にも、生きている分岐と終わった分岐の区別がつきません。

## 消す条件はあとからでは決まらない

決めるなら足す時点です。何が起きたらこのフラグは要らなくなるのか、誰が消すのか、オンにしたあといつまで分岐を残すのか。

寿命の違うフラグを同じ置き場所にまとめると、見ただけでは区別がつきません。出したら消すリリースのフラグと、ずっと残る権限のフラグを、名前の付け方や置き場所で分けておくと、あとから消せるものを探せます。

## まとめ

- 未完成をフラグで隠せば、ブランチに抱え込まずに毎日統合できる
- 値がコードの外にあるので、コードを変えずに、人を選んで切り替えられる
- 足すのは簡単で消すのは難しいので、入れる時点で消す条件を決める
