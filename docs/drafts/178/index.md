# フィーチャーフラグ — コードを出すことと機能を見せることを分ける

## 今日のゴール

- 作りかけをブランチに抱え続けると、マージがどんどん重くなると知る
- コードを本番に出すことと機能を見せることは、フラグで分けられると知る
- 消す条件を決めずに足すと、フラグが溜まって消えなくなると知る

## 作りかけの機能は人に見せられない

新しい機能を作っている途中、画面は中途半端な状態になります。ボタンはあるのに押しても何も起きなかったり、フォームが最後まで作れていなかったりする、あの状態です。人に見せるのは、ひととおり動くようになってからにしたいところです。

チームで開発すると、これは好みの問題ではなくなります。統合先（チーム全員の変更が集まるブランチ）に入ったコードは、いずれそのまま本番に出ていって利用者に見えます。

だから作りかけの機能は統合先に入れられません。完成するまで自分のブランチに置いておく。それが自然な進め方に見えます。

## 抱えたブランチは統合先から離れていく

ところが、抱えているあいだも他の人は統合先を変え続けます。自分のブランチは日が経つほど周りから離れていきます。そのズレは、マージのときにまとめて解消することになります。3日分と3か月分では、衝突の数も1件ごとの難しさも変わります。

毎日こまめに統合先へ入れれば、ズレは小さいうちに解消できます。でも今度は、作りかけの機能が本番に出てしまいます。

- **完成まで抱える**: 見せずに済むが、マージがどんどん重くなる
- **毎日入れる**: マージは軽いが、作りかけが利用者に見えてしまう

どちらを選んでも困ります。この板挟みの原因は、**本番にコードがあることと、機能が利用者に見えることが、くっついている**ことです。ここを切り離せれば、毎日入れながら見せずに済みます。

## 分岐をひとつ挟んで隠す

これを切り離すのが**フィーチャーフラグ**です。フィーチャートグルとも呼ばれます。やることは、機能をひとつの分岐で包むことです。

```jsx
import { isEnabled } from "./flags";

export default function OrderPage() {
  return (
    <div>
      <OrderSummary />
      {isEnabled("new-payment-flow") && <NewPaymentFlow />}
    </div>
  );
}
```

これで新しい決済フローのコードは本番に入っていますが、`isEnabled` が false を返すあいだ画面には出てきません。作りかけでも、オフのままなら毎日統合先に入れられます。マージを小さく保ちながら、機能は隠しておけます。

未完成をフラグで隠しながら、小さくこまめに統合先へ入れ続ける進め方を**トランクベース開発**と呼びます。長生きするブランチを作らないのが狙いです。

完成したらオンにします。コードはすでに本番に入っているので、公開の日は開発の都合と切り離して選べます。

## 値がコードの外から来る

この切り替えを支えているのは、`isEnabled` が返す値が**コードの中に書かれていない**ことです。値の置き場所は環境変数だったり、データベースや専用のサービスだったりしますが、どれにしてもコードの外にあります。だからオンにするとき、コードもビルドも触らずに済みます。

値をコードに書いてしまうと（`const ENABLED = false` のように）、それはフラグではなく普通の分岐です。切り替えるたびにコードの変更とビルドが必要になり、「毎日入れて、見せずに待つ」が成り立ちません。

さらに置き場所によっては、**人によって違う値を返せます**。

- **環境変数**: いちばん手軽。ただし値を変えるには再起動が要り、全員が同じ値になる
- **データベースや専用のサービス**: 値を変えるとすぐ反映され、利用者ごとに変えられる

人によって値を変えられると、公開を少しずつ広げられます。まず社内の人だけオン、次に利用者の1%、10%と様子を見ながら広げ、問題が出たら値をオフに戻す。ビルドも配り直しも待たずに、壊れた画面を引っ込められます。

使っているアプリで、隣の人にはもう出ている新機能が自分にはまだ出ていない、ということがあります。あれはこの出し分けの途中です。コードはすでに全員に届いていて、見せる相手だけを少しずつ広げています。

似た言葉に**カナリアリリース**があります。あちらは新しいバージョンを一部のサーバーにだけ配って、そこへアクセスを少しだけ流す方法です。バージョンまるごとが単位で、切り替えるのはインフラ側です。フラグは機能ひとつが単位で、コードの中で切り替えます。

## 4つの使い道

ここまでは新機能を出すためのフラグでしたが、同じ仕掛けは別の目的にも使われます。よく知られた整理では4つに分かれます。

| 種類 | 何のために | 寿命 |
|---|---|---|
| リリース | 未完成のコードを本番に置いておく | 短い。出したら消す |
| 実験 | A/B テストのように、利用者を分けて比べる | 一時的。決まったら消す |
| 運用 | 負荷が高いときに重い機能を止めるなど | 長い |
| 権限 | 契約プランや役割によって出し分ける | ずっと残る |

同じ `if (flag)` でも、寿命と切り替えの頻度が違います。数日で消すつもりのものと、ずっと残るものを同じ扱いにすると、あとで区別がつかなくなります。

A/B テストも、多くの場合この実験用のフラグとして実装されます。仕組みは同じ `if` 文で、どちらを見せるかを乱数で振り分けて、あとで結果の数字を比べます。

## 足すのは簡単で消すのは難しい

フラグを足すのは簡単です。分岐をひとつ書くだけです。難しいのは消すほうです。オンにして問題が出なければそのまま動いてしまうので、わざわざ触る理由がありません。放っておくと誰も消しません。

そして数が増えると、分岐は掛け算で増えます。

| フラグの数 | 組み合わせ |
|---|---|
| 1 | 2 通り |
| 3 | 8 通り |
| 10 | 1024 通り |

全部を試すことはできません。手が回るのはごく一部で、残りの組み合わせは、動くかどうか誰も確かめないまま本番に置かれています。

役目を終えたフラグが、放っておいて消えることもありません。オフのまま残った古い分岐は、値がひとつ変われば動き出せる状態で居座り続けます。コードを読む人にも、生きている分岐と終わった分岐の区別がつきません。

## 足す時点で消す条件を決める

だから、足す時点で決めておきます。何が起きたらこのフラグは要らなくなるのか、誰が消すのか、オンにしたあといつまで分岐を残すのか。

上の表の「寿命」の列が効くのはここです。ずっと残る権限のフラグと、出したら消すリリースのフラグを、同じ名前の付け方や同じ置き場所で管理すると、どれが消せるのか分からなくなります。

## まとめ

- 未完成をフラグで隠せば、ブランチに抱え込まずに毎日統合できる
- 値がコードの外にあるので、コードを変えずに、人を選んで切り替えられる
- 足すのは簡単で消すのは難しいので、入れる時点で消す条件を決める
