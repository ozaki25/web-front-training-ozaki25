# リッチテキストの持ち方 — 入れた HTML がそのまま残るわけではない

## 今日のゴール

- リッチテキストエディタが、文章を HTML 文字列ではなく構造として持っていると知る
- スキーマに定義のないタグや属性は、その構造に入れないと知る
- 定義外が落ちるのはエディタを通したときだけで、防御にはならないと知る

## 太字のある文章をどう保存するか

見出しを付けたり、一部を太字にしたりできる入力欄を作ることになったとします。書いた内容はデータベースに保存して、あとで表示し直します。

素直に考えると、保存するのは HTML の文字列です。

```html
<h2>買い物メモ</h2><p>週末に<strong>牛乳</strong>を買う。</p>
```

こうしたエディタでよく使われるのが Tiptap です。Tiptap に上の HTML を渡して、そのまま取り出してみます。

```js
import { generateJSON, generateHTML } from "@tiptap/html";
import StarterKit from "@tiptap/starter-kit";

const html = '<h2>買い物メモ</h2><p>週末に<strong>牛乳</strong>を買う。</p>';

const json = generateJSON(html, [StarterKit]);
console.log(generateHTML(json, [StarterKit]));
// <h2>買い物メモ</h2><p>週末に<strong>牛乳</strong>を買う。</p>
```

同じものが出てきました。ここまでは、文字列をそのまま抱えているように見えます。

## 入れたものが出てくるとは限らない

同じことを、少し汚れた HTML でやってみます。

```js
const dirty =
  '<p>ふつうの文</p>' +
  '<script>alert(1)</script>' +
  '<marquee>流れる</marquee>' +
  '<p onclick="steal()">クリック</p>';

console.log(generateHTML(generateJSON(dirty, [StarterKit]), [StarterKit]));
// <p>ふつうの文</p><p>流れる</p><p>クリック</p>
```

`<script>` は中身ごと消えました。`<marquee>` は `<p>` になり、`onclick` も落ちています。

入れた文字列がそのまま保管されているなら、こうはなりません。一度別の形に変換されていて、出すときに作り直されています。

## 文字列ではなく構造として持っている

変換された中身を見ると、何が起きているか分かります。

```json
{
  "type": "doc",
  "content": [
    { "type": "heading", "attrs": { "level": 2 },
      "content": [{ "type": "text", "text": "買い物メモ" }] },
    { "type": "paragraph", "content": [
      { "type": "text", "text": "週末に" },
      { "type": "text", "marks": [{ "type": "bold" }], "text": "牛乳" },
      { "type": "text", "text": "を買う。" }
    ] }
  ]
}
```

タグの並びではなく、入れ子になった部品の木になっています。

`doc` の中に `heading` と `paragraph` があり、その中に `text` がある。太字は `<strong>` というタグではなく、その文字に付いた `bold` という**マーク**として表されています。

この形は Tiptap が勝手に決めているのではなく、**スキーマ**という定義に沿っています。どんな種類の部品が存在してよいか、どれがどれの中に入れるか、どんな属性を持てるかが、あらかじめ書かれています。

StarterKit という標準セットの場合、定義されているのはこれだけです。

| 種類 | 定義されているもの |
|---|---|
| ノード（部品） | doc, paragraph, heading, text, bulletList, orderedList, listItem, blockquote, codeBlock, horizontalRule, hardBreak |
| マーク（文字に付く装飾） | bold, italic, strike, underline, code, link |

`script` も `marquee` も `img` も、この一覧にありません。定義にない部品は作れないので、変換の時点で消えるか、いちばん近い定義（段落）に寄せられます。属性も同じで、定義されていない `onclick` は持てません。

出すときの HTML は、この木から組み立て直したものです。**入れた HTML の写しではありません。**

## 保存は JSON でも HTML でもよい

こうして持っている中身は、そのまま JSON として取り出せます。HTML として取り出すこともできます。

```js
editor.getJSON();  // 上のような木
editor.getHTML();  // <h2>買い物メモ</h2><p>…</p>
```

公式ドキュメントは、どちらで保存してもよい（both work fine）としたうえで、選ぶ理由を並べています。

- **JSON**: 走査しやすい。たとえば本文中のメンションを探すような処理が書きやすい。エディタが内部で使っている形に近い
- **HTML**: ほかの場所でそのまま描画しやすい。メールに載せるなど。広く使われている形なので、あとでエディタを乗り換えるときに移しやすい

どちらを選んでも、エディタを通った時点でスキーマによる整理は済んでいます。HTML で保存する場合も、保存されるのは利用者が入力した文字列ではなく、木から組み立て直した HTML です。

## 落ちるのは通したときだけ

ここまでを読むと、Tiptap を使えば危ないタグは勝手に消えるように見えます。**これは危険な読み方です。**

消えたのは、エディタの変換を通したからです。通していないものには何も起きません。

保存 API は、ブラウザからのリクエストを受け取るだけです。攻撃する側は画面のエディタを使う義務がなく、好きな中身をそのまま API へ送れます。JSON で保存していれば、スキーマにない種類の部品を含む JSON を組み立てて送れます。

公式ドキュメントも、この点をはっきり書いています。セキュリティを理由に JSON と HTML のどちらかを選ぶ理由はない、悪意ある内容を送りたい人にとってはどちらでも同じで、そもそも Tiptap を使っているかどうかも関係ない、入力は常に検証すべきだ、と。

エディタの変換は、**書く人が間違って壊れた構造を作らないための仕組み**です。送られてきた内容を信用してよいという保証ではありません。受け取る側で、定義どおりの構造かを確かめる処理が別に要ります。

## 値までは見ていない場合がある

もうひとつ、スキーマが見ているのは構造であって、中身の値ではありません。

たとえばリンクは、`href` という属性を持てると定義されています。そこに何が入っていてもよいかというと、そこは拡張ごとの実装しだいです。Tiptap のリンク拡張は、受け付けるスキームを絞っています。

```js
'<p><a href="https://example.com">example</a></p>'
// → <a target="_blank" rel="noopener noreferrer nofollow" href="https://example.com">example</a>

'<p><a href="javascript:alert(1)">押して</a></p>'
// → <p>押して</p>   リンクが外れ、文字だけ残る
```

これは拡張がやっている検証であって、スキーマの仕組みが自動で保証しているものではありません。自分で拡張を書いて属性を増やすときは、その値を誰が確かめるのかを決める必要があります。

## まとめ

- エディタは文章を HTML 文字列ではなく、スキーマで定義された部品の木として持っている
- 定義にない部品や属性はその木に入れないので、変換を通すと消える
- 消えるのは通したときだけで、サーバーへ直接送られた内容には効かない
