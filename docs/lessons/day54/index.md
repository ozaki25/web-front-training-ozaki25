# Day 54: AI-DLC — AI が計画を立て、人間が承認する開発サイクル

## 今日のゴール

- AI-DLC は AWS の方法論で、その実装を自分のエージェントに入れて使うと知る
- 5フェーズ33ステージをスコープで間引き、ゲートで区切って進むと知る
- ゲートを外せる条件は「正しさを機械で検査できるか」だと知る

## AWS が出した AI 前提の開発方法論

**AI-DLC**（AI-Driven Development Life Cycle）は、AWS が2025年に公開したソフトウェア開発の方法論です。リポジトリは「なぜ要るか」をこう書いています。行き当たりばったりの AI コーディングは、プロジェクトが本気になるまでは動く。その先で、プロンプトのあいだで文脈がずれ、判断の理由が記録に残らず、頼んでいないことをモデルが静かにやる。

AI-DLC はここに構造を入れます。ライブラリでもサービスでもなく、スクラムのような「進め方」の仲間で、それを AI 前提に作り直したものです。出発点として AWS は、個別作業の補助も、要件を渡して丸ごと作らせる自動生成も、どちらも速度と品質で十分な結果を出せていない、という観察を挙げています。

実物は2層に分かれています。

| 層 | 決めること | 実体 |
|---|---|---|
| 方法論 | 何をするか | AWS が公開している解説と定義の文書 |
| 実装 | どうやるか | `awslabs/aidlc-workflows` が配布する規則一式 |

実装は1つの定義から生成され、Claude Code、Kiro、Codex CLI、Cursor、opencode、GitHub Copilot の上でそのまま動きます。現行版は **Workflows 2.0（v2）** で、先行していた v1 のワークフロー層を作り直して正式公開されたものです。

この記事は v2 を基準に説明します。フェーズやステージの数も現行版のもので、更新がかなり速いので、実際に触るときは同梱のドキュメントで確かめてください。

AI-DLC が想定しているのは、複数のチームで作るような複雑なシステムの開発です。単純なものならローコードやノーコードで足りるので対象にしない、と AWS 自身が線を引いています。

## 中心の型 — AI が計画して人間が承認する

AI-DLC のすべての活動は、1つの型の繰り返しです。**AI が計画を作り、確認の質問をし、人間が承認してから実装する。**

ふだんの AI の使い方とは、会話の向きが逆です。人間が細かく指示するのではなく、AI が大まかな意図をタスクに分解し、案とトレードオフを出し、判断を人間に聞きにきます。人間の仕事は指示することではなく、節目ごとに検証し、選び、決めることに変わります。

AWS はこれを Google マップに例えています。目的地を決めるのは人間、道順を出すのはシステム、走っているあいだ監督するのは人間。

AI に渡す指示の実例も公開されています。

> 作業に取りかかる前に計画を立て、手順を md ファイルに書け。各手順にはチェックボックスを付けろ。確認が必要な手順には、私に聞くための注記を入れろ。**重要な判断を自分で下すな。** 計画ができたらレビューと承認を求めろ。承認したら、その計画を1手順ずつ実行し、終わるたびにチェックを入れろ。

重要な判断を AI にさせない。承認が出るまで動かさない。この2つが型の芯です。v2 はこれをワークフローに組み上げたうえで、ステージの内側にもうひとつのループを足しています。**AI が作り、AI が検証して直す**。人間の承認は、その外側の節目に置かれます。この内側のループが v2 の肝なので、最後の節で仕組みを見ます。

- **Initialization（0.1〜0.3）**: 作業場所の準備と状態の初期化。3ステージとも自動で終わり、承認ゲートはありません
- **Ideation（1.1〜1.7）**: 作る価値があるかを固めます。意図の把握、実現性の評価、範囲の定義、体制、承認
- **Inception（2.1〜2.9）**: 要求を精緻化します。既存システムのときはまずコードを構造のモデルに起こし、要求分析、ユーザーストーリー、ドメイン設計と進んで、仕事の塊への分解（2.7）とデリバリー計画（2.9）で締めます
- **Construction（3.1〜3.7）**: 機能設計から始めて、コード生成、最後に全体のビルドとテスト
- **Operation（4.1〜4.7）**: デプロイ、監視、性能検証。最後の 4.7 から Ideation へ戻るフィードバックの輪があります

図のフェーズを流れていく仕事そのものにも、大きさごとに名前が付いています。

- **Intent**: 何をしたいかの一文。Ideation の入口で捕まえて、要求に精緻化していく
- **Unit**: Intent を分けた、独立して作れる塊。Inception の終盤で分解され、Construction の設計はこの単位で繰り返す
- **Bolt**: Unit をいくつか束ねた、届ける区切り。スプリントに似た計画の単位だが、実行の順番は Unit どうしの依存関係から決まる

各ステージには担当エージェントが割り当てられています。全部で14体です。

- 専門家が **11体**。プロダクト、アーキテクト、開発、品質、運用など
- レビュアーが **2体**。成果物に READY / NOT-READY の判定を書くが、参考情報で、決めるのは常に人間
- 構成を組むものが **1体**

節目は2種類あります。

- **承認ゲート**（ステージの終わりごと）: 人間が、承認するか修正を求めるかを選ぶ
- **検証ゲート**（フェーズの境目）: 機械が、成果物のリンク切れや対応の抜け（要求に対応するストーリーがない等）を自動で検査する

成果物は `requirements.md`、`stories.md`、`unit-of-work.md` のような md ファイルとしてリポジトリに残り、次のステージが読む文脈になります。どのステージが何を決めたかを細かく記録する監査ログも、一緒に残ります。

## `/aidlc` と打ってから終わるまで

導入は、リポジトリが配布している自分のエージェント向けの一式をプロジェクトにコピーするだけです（Claude Code なら `.claude/` と `aidlc/` の2つ）。あとはチャットで `/aidlc` と打つところからすべてが始まります。

AWS のアカウントは要りません。モデルもいま使っているセッションのものがそのまま使われます。

ガイドに載っている実走の例で追います。お題は「在庫管理の REST API を作る」です。

1. `/aidlc 在庫管理の REST API を作りたい` と打つと、「新機能の開発なので33ステージ全部を通します」という進め方の提案が返ってきます。承認するか、もっと軽い進め方に変えるかを選ぶと開始です
2. あとはステージごとに同じことの繰り返しです。エージェントの質問に答えると要求やユーザーストーリーの文書が作られ、ステージの終わりに承認ゲートが出ます。成果物と残っている指摘（「成功基準に期限がない」など）が表で示されるので、受け入れて進むか、修正に戻すかを選びます
3. 既存のシステムに手を入れる仕事なら、この途中で**逆解析**のステージが動き、コードを部品と繋がりの構造に起こしてから先へ進みます。AI にコードをそのまま読ませず、短く正確な文脈にしてから渡すためです
4. 実装に入ると、まず端から端まで通る一番細い1本（**walking skeleton**）ができます。これは必ず人間が見ます。承認した直後に一度だけ、**残りも毎回見るか、任せて進ませるか**を聞かれます。任せても、失敗すれば必ず止まって聞きにきます
5. 最後に全体のビルドとテストが走り、要求からコードまでの成果物一式が md ファイルとして `aidlc/` の下に残ります。セッションを閉じても、次に `/aidlc` と打てば続きから再開できます

流れの全部で、決めるのは人間で、作るのは AI です。中心の型が、そのままワークフローの形になっています。

## 承認ゲートの粒度 — Construction が今の形になるまで

実装フェーズの「1つのステージを全 Unit ぶん回してから、ゲートを1回置く」という進め方は試行錯誤の産物で、ガイドに経緯が書かれています。

- **最初**: Unit ごと・ステージごとにゲート。Unit が3つなら、テスト済みのコードが1行も出る前に**15回のゲート**。顧客は「お守り（babysitting）」と呼んだ
- **次**: 全 Unit ぶんまとめて進めて、レビューは最後に1回。15 Unit の実行で **15,000行のコードが1つのゲートに一度に届いた**。1回のレビューで見られる量ではない
- **いま**: 1ステージを全 Unit ぶん回してゲート1回。その中間

ゲートは細かいほど安全ですが、そのぶん人間が詰まります。粗いほど速いですが、1回の判断に載る量が人間の限界を超えます。承認ゲートの数は、安全と速度のトレードオフとして選ばれています。

## スコープ — 始める前に何に同意するかが分かる

33ステージが毎回すべて走るわけではありません。仕事の種類ごとに**スコープ**が用意されていて、同じエンジンのまま実行するステージを間引きます。全部で11種類です。

| スコープ | 実行ステージ | 用途 |
|---|---|---|
| `enterprise` | 33 / 33 | 規制のある企業向け機能。完全な監査証跡 |
| `feature` | 33 / 33 | 新機能のフルライフサイクル |
| `mvp` | 23 / 33 | 新規開発。後半の運用ステージを省く |
| `poc` | 8 / 33 | 実現性を素早く確かめる |
| `bugfix` | 9 / 33 | 特定のバグを直して出す |
| `classic` | 26 / 33 | Ideation を省いた構成（初版 v1 相当）。既定 |

深さも3段階（Minimal / Standard / Comprehensive）あり、各ステージが成果物をどれだけ詳しく書くかを変えます。poc と feature とでは、儀式の量が桁で違います。まず触ってみるだけなら、8ステージの `poc` から始められます。

始めるときの確認には、実際に走るステージ数と、人間が判断する回数が出ます。この数字は AI の見積もりではなく、定義から計算した確定値です。**何回付き合わされるのかを知ったうえで始められます。**

## 直した内容がルールになって残る

途中で AI の解釈を直すことは、必ず起きます。v2 はその修正を使い捨てにしません。

ステージの実行中、エージェントは判断の日記を付けています。曖昧だった箇所をどう解釈したか、指示からどこで逸れたか、どんなトレードオフを選んだか。

1. 承認ゲートの手前で、その日記が候補として提示される
2. 残す価値のある修正を人間が選ぶ
3. 選ばれた修正が**ルールとしてファイルに書き込まれ**、次のワークフローから効く

ガイドの例は銀行のプロジェクトです。「トランザクション」をデータベースの意味に取り違えたエージェントを人間が直し、その解釈をルールとして残すと、次からは最初のステージから正しい意味で通じます。

効くのは次のワークフローからで、実行中には効かせません。途中でルールが変わると、すでに通したゲートの前提が崩れるからです。

ルールとは別に**センサー**という機械の検査もあります。ステージが成果物を書くたびに、リンタ、型検査、必須の見出しの有無といった決定的なチェックが自動で走ります。ルールが「こう書け」と前から効くのに対して、センサーは「そう書けたか」を後ろから確かめます。この版では結果は助言扱いで、ゲートを止めはしません。

## ゲートを外せる条件

v2 の回し方は二重のループです。ステージの内側では **AI が実装し、AI が自分の出力を検証して直す**ことを繰り返し、収束したものだけが外側の承認ゲートで人間に届きます。内側のループが信頼できる範囲が広がるほど、外側のゲートは減らせます。

その線引きの基準が「**正しいと機械で確かめられるか**」です。

仕様は各段階を3つの区画で定義します。

| 区画 | 決めること |
|---|---|
| 1 | 何を入れて、何を出すか |
| 2 | 正しいとどう分かるか（事後条件） |
| 3 | 実行から何を学び、次の事後条件の候補にするか |

**事後条件がなければ、AI は自分の出力を直せません。** 逆に事後条件が機械で検査できるなら、AI は自分で検証して直すのを繰り返せます。ビルドとテストのように白黒がつく段階は、そこまで到達できます。さきほどの学習ループは、3つ目の区画（実行から学ぶ）が実装に現れたものです。

事後条件は、LLM への指示として自然言語で書くこともできます。コードレビューの観点のように、白黒がつかないものはそうなります。

ただし仕様はここに釘を刺しています。**同じモデルが答えを作り、その答えを採点すると、チェックの文面は満たすが意図は満たさない出力に収束する危険がある。**

だから事後条件が LLM の判断だけの段階は、自分で完了させずに人間の検証へ出します。「本番環境を消すコードパスを作らない」のように外せないものは、専用のリンタや静的解析で決定的に見ます。そして自己修正のループには、反復回数かトークンの予算で必ず**停止条件**を置き、収束しなければ人間に戻します。無限に回り続けるのも、要らない場面で人間を待たせるのも防ぐためです。

この基準は、AI-DLC を導入していなくても使えます。AI にどこまで任せるか迷ったときは、「正しいと機械で確かめられるか」で線を引けます。

## まとめ

- AI-DLC は AWS の開発方法論。AI が計画して作り、人間は節目で承認する
- v2 は5フェーズ33ステージを、スコープで間引き、ゲートで区切り、修正をルールとして貯める
- 外せるゲートは、正しさを機械で検査できるところだけ
